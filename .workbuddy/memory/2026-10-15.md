## 「N12 到 P8 不走 C4 了怎么办」—— 根因是长度改了，不是权重坏了（只分析，未改代码）
- **现象**：报告里一轮去程 `N12→P8` 走楼梯侧 `N12 N16 N18 B5 N19 C6 B7 N22 B6 N20 P8`，不再走历史手写 `rout_58` 的南环 `…N10 N9 C3 N14 B10 C7 C8 B11 C4 N20 P8`。

## L6406E 链接失败诊断：ROM 超了 1008 字节（不是配置错，是真容量墙）
- 现象：`-b` 报 47 个 `L6406E: No space in execution regions with .ANY selector` + `L6407E: aggregate size 0x128 bytes could not fit`。**47 条错误全是同一个根因**（放不下的段被逐个点名），不要逐条查。
- ⭐ **根因：芯片只有 64KB Flash**。`Mcu.CPN=STM32F750V8T6`（V8 = 64KB，**不是** 512KB —— 网上多家卖家的"512KB"是错的，ST 官方 Value Line 明确 F730/F750/H750 = 64KB）。所以 `<OCR_RVCT4><Size>0x10000</Size>` 的 64KB 限制是**正确的**，不能改大。
- ⭐ **改 IROM 无效 ⇒ 认错对象了**：改 `<IROM>` 块或 `<Cpu>IRAM(...-0x801FFFF)` 行都**不生效**，链接照旧失败（Max 仍是 0x10000）。真正决定 ER_IROM1 上限的是 **`<OCR_RVCT4>`**（StartAddress 0x8000000 / Size 0x10000）。`<IROM>`/`<OCR_RVCT1..3>` 都是 0（未用）。**诊断时改 `<OCR_RVCT4>` 临时放到 0x20000 就能链接成功、读出真实 Program Size** —— 这是本项目的标准诊断手法。
- 实测（每档都是真跑 Keil `-r` 得到的数字，不是估算）：
  | 配置 | Code+RO+RW | 相对 64K |
  |---|---|---|
  | 当前基线（COMP 场 / STEP_DEBUG=1） | 66544 | **超 1008** |
  | STEP_DEBUG=0 | 66420 | 超 884（**只省 124，别指望它**） |
  | 切 FIELD_SCHOOL | 66544 | 0（场地切换不产生代码，两场地共用逻辑） |
  | Optim 0→3(O2) | 64984 | **反而更大**（oTime=size 也一样大） |
  | **去掉浮点 printf（%f→%d）** | **63420** | **省 2224，一击致命** |
- ⭐ **最大的杠杆是 ARMCC 的浮点 printf**：只要有**一处**活着的 `%f/%e/%g` 就把 `mc_w.l(printfa.o)`（2218 字节）整个拖进来。本项目活着的浮点 printf 只有 **9 处**（`chassis_api.c` 424/432/731/817/840/870/888 + `barrier.c` 293/350），其余 20 处早被注释掉了。
- ⚠️ **不要用 `-O2` 救**：本工程 O2 比 O0 **还大 1~7KB**（O1 最大 76764），因为大量 `float` 局部变量 + 未初始化分支，O2 展开/内联后反而膨胀。`<Optim>` 改 0→3 确实生效（barrier.o md5 变了）但体积变大，无收益。
- ⚠️ 诊断时改 `Application/chassis_api.c`/`Mission/barrier.c` 会把整文件 CRLF→LF（Edit 类工具的坑），**用字节级替换**，收尾回读行尾。
- 修复方向（待用户拍板）：把 9 处浮点 printf 的**格式符**改成定点整数（如 `%.1f` → 传 `(int)(x*10)` 配 `%d` 并在串里标注单位），既能保住排障信息又能甩掉 printfa.o；不要直接注释掉 —— 这些是 `[PROTECT]`/`[HANG]` 现场排障的唯一证据。

## 回答「之前没超啊，最近加了什么」—— 是 STEP_DEBUG，不是新功能
- 三次构建的 ROM 账：15:16 最后成功 **65276（只余 260！）** → 16:37 失败 **66544（超 1008）** → 现在 **62932（余 2604）**。
- ⭐ **15:16 那次成功时就已经只剩 260 字节**，本来就站在悬崖边 —— 所以"最近没加什么大功能也超了"是正常现象，不是 bug。
- 15:16→16:37 之间 Code **+1252**、RO +20。逐个开关实测归因（删 printf 后重测，各开关单独开）：
  | 开关 | Code | ROM | 相对当前 |
  |---|---|---|---|
  | 当前 STEP_DEBUG=1 / TIME_BUDGET=0 | 58152 | 62932 | — |
  | TIME_BUDGET_ENABLE 0→1 | 58544 | 63324 | **+392** |
  | STEP_DEBUG 1→0 | 58036 | 62808 | **-124** |
  ⇒ 16:37 那次 +1252 的主要来源是 **`STEP_DEBUG` 从 0 改成 1**（用户 16:37 亲手改的，config.h mtime 与失败时刻同分钟），加上 TIME_BUDGET 等其它开关翻动的合计。**STEP_DEBUG 单独只贡献 124 字节**，所以真正让它"掉下悬崖"的是它把原本仅剩的 260 字节余量吃穿。
- 结论口径：这个工程 ROM 余量长期在**几百字节**量级，任何开关翻动都可能触发 L6406E。以后每轮改完都该看 `Program Size` 的余量，而不是等链接报错。
