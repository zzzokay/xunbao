# 预设路线 + 任意步骤启动（状态快照回放）设计方案

> 目标：把现在「按键喂票、从头发车」的单步调试，升级成「离线生成一条完整预设路线 + 固件从任意步骤启动，
> 且从该步骤启动后的状态与完整路线跑到该步骤时**完全一致**」。
> 本文只定规格（目标行为 / 输入输出 / 状态一致性约束 / 执行流程），不改代码。
> 相关文档：`README.md` §1~§9、`project_reference.md` §9/§11/§12/§14、
> 上位机 `tools/sim_route_bookkeeping.py`、`tools/trace_rounds.py`。

---

## 0. 一句话结论

**「步骤」= 一条边**。把「完整跑一遍时每一步入口处的全部可变状态」离线算出来并写成快照，
固件不再从头跑，而是**直接加载第 k 步入口状态**再交给原有 `Navigation()` 继续跑。
一致性不是靠"再跑一遍凑出来"，而是靠**逐字段还原 + 逐字段校验**。

**打断源已明确（本方案的前提）**：人为避险抬车 ⇒ 触发丢线保护（语音 30）/ 横滚保护（语音 31）
⇒ `while(1)` **终态死停，唯一出路是断电复位** ⇒ 全部 RAM 状态丢失。
⇒ 快照不是"调试便利设施"，而是**扛掉电的续跑凭据**：必须编译进 Flash 常量表，且必须支持从任意步恢复。

## 1. 现状：单步调试怎么实现的、为什么还会被意外打断

### 1.1 现有机制（`STEP_DEBUG=1`）

| 环节 | 位置 | 行为 |
| --- | --- | --- |
| 计票 | `Task/motor_task.c:97-114` | `key[0].mode==1`（短按）计入 `nav_burst`；`NAV_TOKEN_WINDOW_MS=2000`（`config.h:96`）滚动窗口关闭后一次性 `nav_token += nav_burst` |
| 门控 | `Navigation/map.c:599-620` | 仅在 `nav_step == NAV_STEP_INIT`（新边开始）且 `route[map.point] != 0xFF` 时检查 `nav_token`；无票则 `Chassis_Brake()` 后 `return`（停车等票） |
| 扣票 | 同上 | 有票 `nav_token--`，放行**一条边** |

⇒ 步的粒度天然就是「一条边 = 一次 `Navigation()` 的 INIT→MID_SWITCH→PREP_ARRIVE→NEAR_END→`Nav_TurnAndAdvance()` 推进」。

### 1.2 打断源：人为抬车 → 保护死停（不是时间、不是障碍）

单步调试时人必须贴近车，必要时把车**抬起来避险或搬运**。抬车会让**轮子离地 / 车身倾斜 / 巡线板看不到线**，
直接命中两条**默认开启**的保护（`Chassis_Init` 里使能，`chassis_api.c:141-142`）：

| 保护 | 触发判据 | 位置 | 后果 |
| --- | --- | --- | --- |
| **丢线保护** | `Scaner_IsLineLost()`（整段巡线历史全无效，`scaner.c:89-97`）连续 `LINE_LOST_THRESHOLD=80` 次（0.4s） | `chassis_api.c:803-826` | `line_lost_enabled=0`（一次性）+ `CarBrake()` + 播报 **30** + `printf("[PROTECT] LINE-LOST-STOP …")` + **`while(1){}`** |
| **横滚保护** | `fabsf(imu.roll - basic_r) > 40.0f` | `chassis_api.c:726-734` | `CarBrake()` + 播报 **31** + `printf("[PROTECT] ROLL-STOP …")` + **`while(1);`** |

（PWM 超限 / 堵转保护同属 `while(1)` 死停，但 `Chassis_EnableStallProtection()` 在 `chassis_api.c:140`
已被注释掉 ⇒ 默认关闭，暂不作为主要打断源。）

**这两条共同的性质才是致命的**：

1. **终态**：`while(1)` 没有任何退出路径；`CarBrake_Stop()`（`chassis_api.c:947`）同理
   ⇒ 现场唯一的出路是**断电 / 复位**。
2. **掉电即失忆**：`route[]`、`map.point`、`nodes`、`door_pass[]`、`Node[]` 覆盖、`s_blocked[]`、
   `treasure_taken`……**全是 RAM 变量** ⇒ 重启后一律归零，等于从头再来。
3. **语音号错位**：30 / 33 号语音没有录音（`chassis_api.c:815` 注释已记录）⇒ 现场表现是"无声停住"，
   必须靠串口 `[PROTECT] …` 才能判断死在哪一步。

### 1.3 另外两个结构性缺陷（放大抬车的代价）

1. **起点被写死**。`mapInit()`（`map.c:87`）恒把 `map.point=0`、`route[]` 重算成 `N2→P1→N5`；
   `zhunbei()`（`barrier.c:2077`）必等两次红外挡板。想看第 30 步只能人工按满 30 票并全程陪跑。
2. **状态是"跑出来的副作用"**，不是可指定的输入：
   - `Node[].function/step/speed` 被 `door_set_pass_node()`（`barrier.c:1646`）和
     `upright_Set_node()/upright_Reset_node()`（`barrier.c:2124/2131`）改过；
   - `door_pass[]`（`barrier.c:72`）只记**车已经读过的**门色，没读过的 = 0（≠ 黑灯）；
   - `treasure` / `treasure_taken`（`barrier.c:94/102`）、`s_exit_checked`（`mission_planner.c:158`）、
     `nav_planner` 的禁边表 `s_blocked[]`（`nav_planner.c:74`）、`route[]` 尾段被重规划过……
   抱着车按票时这些副作用要么没产生、要么被抬车动作污染 ⇒ **"补跑"的状态 ≠ 完整路线到该点的状态**。

### 1.4 结论

打断既然等价于"断电 + 从头再来"，修复方向就不是加强按键门控，而是：
**把"离线可确定的全部状态"预先算出来、编译进 Flash 快照，固件从任意步骤加载进去继续跑。**
于是：① 抬车打断后**不必从头跑**，选断点那一步续跑即可；② 状态逐字段还原 ⇒ 续跑行为与完整路线一致；
③ 抬车本身也不再需要"能不停就别停"地冒险 —— 可以在步边界安全地抬、放、续跑（§7.5）。

## 2. 目标行为

| 编号 | 目标行为 |
| --- | --- |
| **G1 离线生成** | 由上位机 + 既有状态机仿真（`sim_route_bookkeeping.Sim`）在**不碰车**的前提下，生成第一轮 + 第二轮的**完整预设路线**，并输出两种形态：人读清单（逐步表）与机器可读头文件（快照数组） |
| **G2 任意步骤启动** | 固件支持选择 `k ∈ [1, N]`（N = 总步数），从第 k 步入口状态开始执行；`k=1` 等价于现有完整流程 |
| **G3 状态等价（核心）** | 从任意 `k` 启动后，状态轨迹与「完整路线跑第 1..N 步」在 `k..N` 段的轨迹**逐字段一致**；不得出现"少做/重做某个动作、走另一条边、提前/延后定档" |
| **G4 抬车安全（针对打断源）** | ① **预防**：步与步之间提供「暂停-复位」，挂起丢线 / 横滚保护、停电机、冻结推进 ⇒ 抬车 / 搬运**不触发保护**，放下后原位续跑；② **兜底**：保护已触发（`while(1)`）时断电重启，用 `preset_apply(k)` 恢复到当前步或上一步继续；③ 步与步之间**默认自动推进**，可选降级为「每步等票」以观察 |
| **G5 可校验** | 固件启动与每一步都打印可 diff 的 trace；上位机提供脚本把串口 trace 与清单逐行比对，不一致立刻定位到步号 |
| **G6 摆放说明** | 起点为特殊节点时，输出一条物理摆放说明（摆哪、朝哪、哪些前置动作已发生过），供第 ④ 步对位 |

**非目标（本方案不承诺）**：步内（动作中途）存档 —— **抬车只允许在步边界做**，步内抬了就整步重做
（等价性由"步是原子的"保证，见 I7）；跨轮次的动态改配（如现场临时换门色）；
无传感器下自动完成取宝/读门等物理动作（仍依赖现场或 `DEBUG=1` 预设）。

## 3. 术语与坐标

- **边 / 步骤 step k**：一次边执行。`from = nodes.nowNode.nodenum`，`to = nodes.nextNode.nodenum`。
  编号从 1 开始，第一轮与第二轮**连续编号**（第一轮最后一步之后紧接第二轮第 1 步）。
- **步骤入口状态 `S(k)`**：`Navigation()` 中 `nav_step == NAV_STEP_INIT` 且 `route[map.point] != 0xFF` 那一刻的全部
  可变状态（正是现有 `STEP_DEBUG` 的等票点）。**"从第 k 步启动" = 把车摆到第 k 步起点并把状态置成 `S(k)`。**
- **起点节点**：`S(k)` 里的 `nodes.nowNode.nodenum`。
- **特殊节点**：`P1..P8`（平台）、`S1/S2`（直立景点）、`N3/N5/N8/N10/N12`（门区）、
  `N7/N9/N13/N14/N16/N18/N20/N22/B5..B11/C3..C9`（障碍/楼梯/刀山/波动板入口）等**带 `function` 或带副作用的节点**。
  从这类节点启动时，`S(k)` 里必须已包含"前面的动作产生过什么"，否则动作会被重复或跳过。

| 宝物 | `treasure` 或 `flag_clue_A/B`（`treasure = A + B`） | `barrier.c:94` |

### 4.2 输出 1：人读清单（`.txt`）

```
# 配置指纹 field=FIELD_SCHOOL tour=1 punch=1 treasure=P1 clue=3/5/7 doors=[蓝,绿,绿,黑,-]
 step  round  edge         func        point  next  副作用(本步产生的状态变更)
    1     1    P2->N2      NONE          1    N2    -
    2     1    N2->B1      NONE          2    B1    -
   ...
    k     1    N5->N12     DOOR          ?    N12   door_pass[0]=蓝; Node[N5->N12].func->NONE; route[]尾段重规划
   ...
   N=..   2    P2->B3      NONE        ...    B3    路线结束
```

- 每行必须含：步号、轮次、`from->to`、该边 `function`、入口 `map.point`、入口 `nextNode`、以及**本步会产生的副作用**。
- 末尾附「按起点节点索引」的摆放说明表（见 §7.4）。

### 4.3 输出 2：机器可读头文件（`preset_route.h`）

```c
/* 自动生成：勿手改。指纹不匹配时固件拒绝启动 */
#define PRESET_STEP_COUNT      N
#define PRESET_FINGERPRINT     0x5A17C0DE   /* hash(场次, 开关们, 门色, 线索, 宝物) */

typedef struct {
    u8  point;                 /* map.point      */
    u8  routetime;             /* map.routetime  */
    u8  last, now, next;       /* nodes 三元组（节点号） */
    u8  door_pass[5];          /* 车已读到的门色 */
    u8  treasure, treasure_taken;
    u8  flag_line_clue, flag_clue_stage_A, flag_clue_stage_B, flag_clue_A, flag_clue_B;
    u8  exit_checked;          /* mission_planner.s_exit_checked */
    u16 elapsed_s;             /* 该步入口时的已用时（供审计；运行期不复用，见 §6.4） */
    u8  blocked[8][2];         /* nav_planner 禁边表（门区 8 条的子集） */
    u8  blocked_n;
    u8  func_ovr_n;            /* Node[] 覆盖条数 */
    struct { u8 from, to, func; u16 step; } func_ovr[16];
    u8  route[ROUTE_SNAP_LEN]; /* route[] 快照（0xFF 结尾） */
} preset_state_t;

extern const preset_state_t preset_states[PRESET_STEP_COUNT];
```

> `ROUTE_SNAP_LEN` 取 100（与 `u8 route[100]` 同），一格 100B ⇒ 100 步约 10KB Flash，F4 上完全可接受。

### 4.4 输出 3：校验产物

- `preset_trace_expected.txt`：每步一行的**期望串口打印**，供 `preset_verify.py` 与真机 diff。
- 生成脚本自检报告：快照 vs 重算 route 逐字节一致、每步不变量成立、无红线违规。

## 5. 状态清单（状态向量的完整枚举）

**这是本方案的地基**：凡是"会影响下一步走哪条边 / 触发哪个 `function` / 走哪个分支"的可变量，
都必须进快照。下表按影响面分层。

### 5.1 A 类 — 直接决定路线内容（**必须逐字段还原**）

| # | 状态 | 定义处 | 谁在运行期改它 | 不一致会怎样 |

### 5.3 C 类 — **不可离线复现**，必须由现场/物理提供

| # | 状态 | 说明 | 应对 |
| --- | --- | --- | --- |

### 5.4 D 类 — 保护/异常状态（抬车直接相关，**重启后必须显式重新使能**）

| # | 状态 | 位置 | 为什么必须处理 |
| --- | --- | --- | --- |
| D1 | `chassis.line_lost_enabled` | `chassis_api.c:40/803-811` | **一次性**：触发后置 0，且 `while(1)` 锁死；断电重启后由 `Chassis_Init()` 重新置 1（`chassis_api.c:141`）。若沿用旧意图（"已经丢过一次线就不再保护"），抬车第二次就会被静默放过 ⇒ 保护失效 |
| D2 | `chassis.line_lost_count`（连续丢线计数） | `chassis_api.c:41` | 抬车悬空期间会持续累加；放下后续跑若不归零，**0.4s 阈值被"提前用掉"** ⇒ 刚落地就误触发死停 |
| D3 | `chassis.roll_protect_enabled` | `chassis_api.c:44/726` | 同上，抬车时车身倾斜 > 40° 即死停；重启后由 `Chassis_Init()` 重新置 1（`chassis_api.c:142`） |
| D4 | `chassis.stall_protect_enabled` / `stall_count[4]` | `chassis_api.c:48/830/846` | 默认关（`:140` 被注释）；若临时开启，抬车（轮子空转、PWM 拉满）极易触发 `while(1)` |
| D5 | `chassis.anti_snake_flag` / `anti_snake_err_count` | `chassis_api.c:36-38/766-800` | 抬车瞬间偏移大 ⇒ 警戒值飙升，放下后车被"低速压制"跑一段 ⇒ 与完整路线行为不同（B 类，但属抬车污染，务必复位） |
| D6 | `chassis.wheelie_protect_active` / `saved_Cincrement` | `chassis_api.c:51-53/742-761` | 抬车时 `pitch` 超阈值 ⇒ 激活并**覆盖 `motor_all.Cincrement`**；放下后若未复原，加速度被永久压低 |
| D7 | 巡线历史 `line_data[]` / `Scaner.error` / `Scaner.ledNum` | `scaner.c:68-97` | 抬车期间写入的都是无效历史 ⇒ 放下后需 `Scaner_ClearLineData()`（`scaner.h:46`）清零，否则丢线判据被污染 |

### 5.5 E 类 — 抬车会污染、必须校正的物理量

| # | 量 | 抬车时怎么被污染 | 校正动作（放在"放下后、续跑前"） |
| --- | --- | --- | --- |
| E1 | 编码器里程 `motor_all.Distance` / `Chassis_GetMileage()` | 轮子空转或倒转 ⇒ 里程乱走 | `Chassis_ClearMileage()`（`chassis_api.h:181`）。**注意：每步入口 `Nav_SegmentInit()` 本来就会 `Chassis_ClearMileage()`（`map.c:433`）⇒ 只要在步边界恢复，这一项自动归零**（这正是"步=边"设计的第二大好处） |
| E2 | 陀螺仪航向 `getAngleZ()` | 抬车转动车身 ⇒ 航向整体偏移 | `mpuZreset(get_latest_yaw(), nodes.nowNode.angle)`（与 `map.c:62` 同款）；带 `RESTMPUZ` 的边（`ArriveDetect_task.c:31`）运行中还会自校正 |
| E3 | 底盘跟踪/PID 临时覆盖 | 抬车时 `Chassis_OverrideLinePid` 可能残留 | `Chassis_RestoreLinePid()`（清临时覆盖）；彻底一点可直接 `Chassis_Init()` |
| E4 | `cross_event` / `arrive_method` | 到达检测被悬空动作打断 | 复位（已在 B 类） |
| E5 | 电机 PID 积分/输出 | 悬空时输出拉满、积分饱和 | `pid_init()` / `Chassis_SetMode(is_Line)` 重启环 |

> **要点**：E1 由架构自动解决，E2 必须显式做，D 类必须"重新使能 + 清零计数"。这三件事合起来，
> 抬车才从"破坏现场"变成"可插拔的暂停"。

## 6. 状态一致性约束

### 6.1 核心不变量（I 系列，必须逐条成立）

| 编号 | 不变量 | 校验方式 |
| --- | --- | --- |
| **I1 快照完备** | A 类状态清单里的每一项都出现在 `preset_state_t` 里 | 清单 ↔ 结构体字段双向核对（脚本静态检查） |
| **I2 逐字段等价** | `preset_apply(k)` 生效后，固件中 A 类每个字段 == 快照 `preset_states[k-1]` | 启动时打印全部字段并与清单比对 |
| **I3 推进不变量** | 任意步 `route[map.point - 1] == nodes.nextNode.nodenum`（或 `== 0xFF`） | 与 `sim_route_bookkeeping.Sim.check()` 同口径，逐步断言 |
| **I4 后续路线可复现** | 从 `k` 恢复后，任何 `plan_route_at()` 的重算结果与完整路线在同步处的重算**逐字节相同** | 依赖 I1/I2 中 A1、A6、A7、A8、A9 齐备 |
| **I5 副作用不重不漏** | `Node[].function` 覆盖集合、`s_blocked` 集合、`treasure_taken` 与完整路线在 `k` 处完全相同 | 集合相等断言（不是"包含"） |
| **I6 定档不重复** | 从 `k` 启动后 `round1_exit_recheck()` 不再改变路线 | 还原 `s_exit_checked=1` 且快照 `route[]` 已是定档后内容（§6.4） |
| **I7 恢复点粒度 = 步边界** | 抬车与恢复只发生在步边界；步内被打断则该步整体重做 | 快照只存步入口状态 ⇒ 步内恢复在定义上不可表达；"整步重做"与"完整路线该步"等价（步是原子的） |
| **I8 保护状态重新使能** | 每次启动（含断电重启恢复）后 `line_lost_enabled` / `roll_protect_enabled` 均为 1，`line_lost_count=0`，巡线历史已清零 | D 类自检：启动时打印并断言；否则抬车不再被保护，或落地即误触发死停 |

**I2 + I4 + I5 合起来，就是"完整模仿与还原该节点状态"的可判定形式。**

### 6.2 一致性分级

- **L1 强一致（必须）**：A1~A11 全部逐字段相等。
- **L2 弱一致（允许现场决定）**：位置、航向、陀螺基准、物理传感器读数（C1~C4）。
  L2 不满足时**行为允许不同**，但必须在启动时明确打印提示（例如"陀螺基准已按 N5→N12 复位"）。
- **L3 不适用**：B 类复位即可，无需相等。

### 6.3 状态来源唯一化（保证 I1 不完备时能被发现）

一条状态要影响分支，必须**同时**满足：① 在固件里被读；② 在快照里被记。
因此实施时先做一件事：**用清单穷举"所有被 `if/switch` 当作条件的可变全局量"**（A 类就是这份清单），
然后规定 —— 任何人以后新增一个"运行期可变、会被分支读取"的全局，必须同时扩 `preset_state_t` 与生成脚本，
否则 `preset_route.py` 的 I1 自检直接报错。这是防止"跑起来才发现漏了一个标志"的唯一手段。

### 6.4 时间维度的特殊约定（最容易出错的一条）

现状：`Match_Elapsed_S()` 的**唯一消费者**是 `round1_exit_recheck()` → `round1_tail_tier_of()`
（`mission_planner.c:200`），出门时刻已用时决定尾段是否裁剪 S1/S2、补打卡平台、或直接回家。
从第 k 步启动时计时器必然偏小 ⇒ 若不处理，**定档会变成"全量"，与完整路线不一致（违反 G3）**。

**约定（推荐方案）**：
1. 定档**全部在离线阶段完成**：生成脚本按给定"出门已用时"算出档位，把定档后的 `route[]` 写进快照；
2. 快照里 `exit_checked = 1`，固件 `preset_apply()` 把它写入 `mission_planner.s_exit_checked`；
3. 运行期 `Match_Timer_Start()` 仅用于显示/审计，**不再改变路线**；
4. 若起点本身就在定档之前（即还没出门），则快照 `exit_checked = 0`，并额外提供"运行期已用时偏置"
   `match_start_tick -= 偏置`，使 `Match_Elapsed_S()` 从"仿真已用时"继续累加。

> 备选方案：干脆规定"从任意步骤启动时本轮计时归零"，此时必须在文档里明确"时间预算档位可能与实战不同"，
> 且该步骤必须选在定档之后，否则路线会与完整路线分歧 ⇒ 所以仍推荐方案 1。

### 7.1 离线生成流程（上位机）

```
[1] 读指纹    ← Mission/config.h 的场次+开关 + 输入的门色/线索/宝物
[2] 生成路线  ← map_model 现有能力：
                 M.parse_round2_cruise() / M.upright_tour_waypoints() / M.p3p4_punch_waypoints()
                 M.round1_return_extra_waypoints() / _round1_complete() / _round2_route_sections()
[3] 状态机跑  ← sim_route_bookkeeping.Sim 逐跳（已有），本轮新增「逐步快照」：
                 Sim.snapshot() → {route 副本, point, routetime, last/now/next,
                                   door_pass, treasure, treasure_taken,
                                   func_override 拷贝, blocked 拷贝, exit_checked, elapsed}
                 ⚠️ 缺口：Sim 目前只记 route/point/nodes/func_override/door_pass/treasure；
                    treasure_taken、exit_checked、flag_* 需补进 Sim 的记账，否则快照不完整（I1）
[4] 逐步自检  ← I3 不变量 + 红线（既有 + 新增 I2/I5）
[5] 导出      → preset_route.h + preset_route_step_<指纹>.txt + preset_trace_expected.txt
[6] 回放自检  ← 关键验收：对每个 k，用 preset_states[k-1] 在 Sim 里「从 k 起跑」，
                 与完整 trace 的 k..N 段逐行比较，必须 100% 相同（见 §10 A2）
```

`[6]` 是**离线就能证明 G3 成立**的一步，必须在固件动手前先跑通。它等价于把这台仿真当成"参考实现"，
快照回放与完整跑在仿真里等价 = 固件里只要 `preset_apply` 忠实，行为就等价。

```c
/* preset_apply(k)：忠实还原 A 类状态；B 类复位 */
void preset_apply(uint8_t k)
{
    const preset_state_t *s = &preset_states[k - 1];

    mapInit();                     /* 先建图 + 保证 Node[]/规划层有初值（map.c:87） */
    nav_clear_blocked();

    /* A1 */  memcpy(route, s->route, sizeof(route));
    /* A2/A3 */ map.point = s->point; map.routetime = s->routetime;
    /* A4 */  nodes.lastNode = Node[edge_idx(s->last , s->now)];
              nodes.nowNode  = Node[edge_idx(s->now  , s->next)];
              nodes.nextNode = Node[edge_idx(s->next , route_idx_next(s))];
    /* A5 */  重放 s->func_ovr[]：Node[idx].function / step 直接赋值
    /* A6 */  重放 s->blocked[]：nav_set_edge_blocked(from, to, 1)
    /* A7 */  memcpy(door_pass, s->door_pass, 5);
    /* A8 */  treasure = s->treasure; treasure_taken = s->treasure_taken;
    /* A9 */  flag_* 逐个赋值（含 clue_A/B / collected 标志）
    /* A10 */ round1_exit_set(s->exit_checked);   /* 需在 mission_planner.c 新增 setter */
    /* A11 */ 见 §6.4 第 3/4 条

    /* B 类复位 */
    复位 nav_step / nav_idle_braked / cross_event / arrive_method / GyroStableReset_statics
    nav_token = (推进模式 == 手动) ? 0 : 0xFF;

    打印一行： [PRESET] k=.. from=.. to=.. point=.. next=.. doors=..
}
```

**⚠️ `preset_apply()` 里 `mapInit()` 的副作用**：`mapInit()` 会把 `route[]` 重算、`map`/`nodes` 清零、
`nav_clear_blocked()`（`map.c:87-103`）。因此**必须先 `mapInit()` 再覆盖**，顺序不能反。
若 `mapInit()` 里 `nav_init()` 尚未跑过（`s_nav_ready==0`），`Node[]` 还不存在，`edge_idx()` 会失败 ⇒
`preset_apply` 第一句必须是 `nav_planner_setup()`（可把 `map.c:78` 的 `nav_planner_setup` 提为可外部调用）。

### 7.3 推进模式（G4）

| 模式 | 行为 | 用途 |
| --- | --- | --- |
| 自动（默认） | `preset_apply` 后 `nav_token = 0xFF`，`Navigation()` 的等票门控恒放行，连续跑完 `k..N` | 正式验证；**不再被"步间等待"打断** |
| 手动（可选） | `nav_token = 0`，每步需按键给票（复用现有机制） | 逐步观察 |
| 单步到某步停 | 自动跑，但跑到目标步 `STOP_AT_STEP` 后转手动 | 分段调试 |

### 7.4 特殊节点起点的摆放说明（离线生成，随清单一并输出）

对每个"可作为起点的节点"，输出一行：

```
起点 = N5（第 k 步 = N5->N12，func=DOOR）
  摆放：把车放在 N5 节点、车头对准 N5->N12 方向（angle = ANGLE_N5N12）
  前置：door_pass 已按快照还原（D2=蓝）；route[] 已含该步之后的重规划结果
  注意：门灯物理颜色必须与 door_true 一致，否则读灯结果与快照不符 → 门分支分歧
```

规则：
- `function != NONE` 的起点（平台/景点/门/障碍），必须列出"前面已经发生过什么"（取宝 / 景点已做 / 门已读）。
- 曾在完整路线里被跳过（如 `UPRIGHT_NEED_TREASURE` 使去程经过 N16 但不做动作）的节点，
  快照必须体现"这次到该点是做还是不做"，不能只看节点名。

### 7.5 抬车安全流程（本功能存在的真正理由）

#### 路径 A：预防 —— 步间「暂停-复位」（推荐，日常都用这条）

```
[1] 车自动推进；到步边界（Navigation 的 nav_step==INIT，车本来就在等/停）
[2] 按键 → 进入「抬车模式」：
      Chassis_Brake();            /* 停电机 */
      挂起保护：line_lost_enabled=0 / roll_protect_enabled=0
      nav_token = 0;              /* 冻结推进：Navigation 在 INIT 处直接 return */
      打印 [PICKUP] paused at step k (from->to)
[3] 抬车 / 搬运 / 对位（可以任意倾斜、轮子空转、看不到线 —— 都不会触发保护）
[4] 把车放回"要继续的那一步起点"，车头对准 Node[nowNode].angle
[5] 按键 → 退出「抬车模式」：
      Scaner_ClearLineData();                       /* D7  */
      chassis_line_lost_count_clear();              /* D2  */
      mpuZreset(get_latest_yaw(), nodes.nowNode.angle);  /* E2 陀螺重对齐 */
      Chassis_ClearMileage();                       /* E1  */
      Chassis_RestoreLinePid();                     /* E3  */
      Chassis_EnableLineLostProtection();           /* D1 重新使能 */
      Chassis_EnableRollProtection();               /* D3 重新使能 */
      nav_token = 0xFF;                             /* 解除冻结 */
      打印 [PICKUP] resumed at step k
[6] Navigation() 继续 → 行为与完整路线 k.. 段一致（由 §7.1 [6] 的回放自检保证）
```

**为什么必须"冻结推进"**：悬空时若还让 `Navigation()` 跑，`Chassis_DriveDistance_Blocking` / `Want2Go()`
（`chassis_api.c:879`）会等里程而里程不涨 ⇒ 卡死；或轮子空转导致里程虚涨 ⇒ 误判到位。
现有 `STEP_DEBUG` 的等票点（`map.c:604-618`）恰好就是这种"停在 INIT、不动状态"的性质，
所以它天然是个合格的"暂停点" —— 新方案只需把"等票"扩展成"等一个被挂起保护的暂停态"。

#### 路径 B：兜底 —— 保护已触发 → 断电 → 快照续跑

```
[1] 车死停（[PROTECT] ROLL-STOP / LINE-LOST-STOP 已打印，while(1) 里）
[2] 断电、上电（或复位）
[3] 根据串口最后一行 [PRESET] k=.. 判断断点：
      断在【步边界】→ 续跑步号 = k
      断在【步内】（同一个 k 的 [PRESET] 之后没有新行）→ 续跑步号 = k（整步重做，I7）
[4] 改 PRESET_START_STEP = 续跑步号 → 重新编译烧录 → 上电续跑
[5] preset_apply() 从 Flash 快照还原 ⇒ 状态与完整路线该步一致
```

**路径 B 成立的前提正是"快照编译进 Flash"** —— 掉电不丢，这是它区别于"RAM 里临时算一份"的根本价值。

#### 两条路径的关系

| | 路径 A（暂停-复位） | 路径 B（断电+快照续跑） |
| --- | --- | --- |
| 适用 | 主动抬车避险 | 保护已经触发 / 意外断电 |
| 代价 | 按键两次，秒级 | 重新编译烧录 |
| 是否触发保护 | **否**（被挂起） | 已触发 |
| 状态一致性 | 靠 D/E 类校正 + 步边界 | 靠 `preset_apply(k)` 逐字段还原 |

## 9. 风险与坑（结合既有台账）

1. **`s_exit_checked` 是 `static`**（`mission_planner.c:158`）⇒ 必须新增 setter；否则 §6.4 的 I6 无法满足。
2. **`Node[]` 是唯一被两处业务逻辑改的共享表**（门 `barrier.c:1646` + 景点 `barrier.c:2124/2131`）
   ⇒ 快照必须记"被改过的边 + 改后值"，不能只记"景点是否做过"。
3. **`door_pass` ≠ `door_true`**：`door_pass` 是"车已读到的"（未读 = 0）。用 `door_true` 填充会让
   回程/二轮 wp 分支选错（`sim_route_bookkeeping` 里已用两套门状态区分，见其注释）。
4. **`plan_route_at(offset, wp, n)` 会从 `offset` 起覆写 `route[]` 尾段**（`mission_planner.c:75`）
   ⇒ 快照只需保证"入口处 `route[]` + A5/A6/A7/A8/A9 一致"，后续尾段会被同样的输入重算成同样的内容（I4）。
   **但如果漏了任何一项 A 类，重算就会分歧**，这是最隐蔽的失败模式。
5. **`mapInit()` 会清 `nav_clear_blocked()` 与 `route[]`**（`map.c:87-103`）⇒ `preset_apply` 顺序必须先 `mapInit` 后覆盖。
6. **`MAP_DEBUG` 的 `VIA_POINT=0` 语义**（`config.h:93`，`S1=0` 不能当途径点）⇒ 预设路线模式应取代
   `MAP_DEBUG` 调试路线，两者不要同时开。
7. **改开关注释时注意续行**：`config.h` 里 `/* ... */` 跨行注释被误删会变裸代码（README §2.12 记录过）。
8. **改完必跑**：`sim_route_bookkeeping.py`（自带源码同步自检）、`trace_rounds.py`、`validate/` 全套；
   改 `map_model.py` 后跑 `_selftest.py` + `_guismoke.py`（用系统 Python）。
9. **Keil 编译**：`-b` 可能跳过不编，必须确认目标 `.c` 出现在 `compiling` 行；只看 `N Error(s)`。
10. **文档与源码行尾**：三份讲解文档 CRLF；`Mission/config.h` 为 LF+BOM；`Navigation/map_message.c` 为 LF；
    新增 `.md` 应与所在目录一致（本目录 CRLF）。
11. **保护是 `while(1)`，没有恢复路径**（`chassis_api.c:733/819/842/872`）⇒
    任何"现场救回来"的幻想都不成立；要么用路径 A 从源头避免，要么走路径 B 断电。**不要试图给 `while(1)` 加超时**，
    那会让"保护"变成"偶发停车"，破坏既有现场排查口径（README §2.11 的停车标签体系）。
12. **抬车模式必须在步边界生效**：若在步内按下抬车键，`Nav_TurnAndAdvance` / 平台动作正在阻塞中，
    挂起保护会让车在**倾斜状态**下继续动作 ⇒ 必须先把"抬车申请"置一个标志，由 `Navigation()` 在下一个
    INIT 处响应（与 `nav_token` 同一位置），而不是在按键中断里立刻切。
13. **`line_lost_count` 不清零 = 落地即死停**（D2）：悬空 0.4s 就够把 `LINE_LOST_THRESHOLD=80` 用掉大半，
    恢复时若不归零，放下车走两步就触发 ⇒ 现场会误判成"抬车把保护抬坏了"。

## 11. 待确认的决策点

1. **步骤粒度**：确认按「边」定义（与现有等票点一致）？还是需要支持"节点到达时"（= 上一条边结束、下一条边入口）？
   两者在无零长边时一一对应，建议按边。
2. **起点范围**：是否包含"步内"（如门读灯中途、平台动作中途）？建议**不包含**，只支持边边界。
3. **推进模式与抬车键**：默认全自动推进（步间无人干预）+ 一个按键进「抬车模式」？还是保留"每步等票"作为默认？
   建议默认自动、按键可切"抬车/等票"（两者都停在同一个 INIT 点，实现上共用一套）。
4. **时间预算**：确认采用 §6.4 推荐方案（离线定档 + 快照固定）？
5. **快照存储**：编译进固件头文件（推荐，离线可靠），还是串口下发（灵活但要现场联机）？
6. **是否覆盖二轮全程**：本轮二轮无时间裁剪（`round1_exit_recheck` 第 2 行 `if (map.routetime != 0) return;`），
   因此二轮步骤的状态更简单；确认二轮也要能任意步骤启动。
7. **起点选择方式**：宏 `PRESET_START_STEP` 编译期定，还是按键/串口运行期选？建议先宏、后串口。
8. **抬车恢复粒度**：路径 B 的续跑默认落在"步边界 = 上一次打印的 k"？还是允许指定 `k-1`（保守回退一步）？
   建议默认 `k`，并在清单里给出 `k-1` 备选（万一抬车发生在该步极早期）。
