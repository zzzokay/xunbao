## 8.25 赛后总结

这次比赛属实还是经验不够，如果能跑出正常水平肯定是有前三名；主要是在过完第一个红绿灯的时候**提前右转导致寻错线**。

### 一、本身代码问题

1. **路线很多依赖硬补偿**：长度差得多，地图一换就需要大量调试。
   - **解决方法**：优化算法，路口转弯时可以转得丝滑一点，转弯要用线判断自己有没有转到位；寻线一段距离后检查角度是否符合地图路线，如果差太多，很可能走错线了，此时可以考虑原路返回再转一次（不过尽量一次定位）；判断路口的方式可以由一次快照改为多次快照形成完整图像（不过那样估计得改很多）。
   - **当前代码里的应对**（原理、参数可信度、量化依据见 [project_reference.md](project_reference.md) §14）：硬补偿那一列**同时表达了两件事** ——
     ① **真·转弯几何**（`Δ = L·(1−cosφ) + d(判据)`，`L`≈19cm 是"旋转中心→传感器板中心"，与实测相关 **r=+0.71**）**能直接算**；
     ② **段长补偿**（到达门槛是 `里程 ≥ 0.7×step`，`step` 只有 1~18cm 时被**里程提前放行**）**算不出来，只能把段长量准**。
     现在的规则是「**能算就算、不能算保留原值**」+ 一条 **5cm 闸门**（公式与实测差超过 5cm 就退回实测）⇒ **补实测数据不会把已调好的点改坏**。
     ⚠️ **`TURN_CALC_ENABLE` 当前 = 0（这套机制没在跑）**，车走"实测表 + 默认 19"的老行为；`N13→N18→B5=60` 那行是 `//` 注释掉的无效条目，别照抄。
     💡 **最小验证动作（不用写代码）**：拿尺子复核 5 条 `step ≤ 18cm` 的段（`B8→N9`=1、`B9→N7`=5、`P8→N20`/`B2→N4`=12、`P6→N7`=18）。

2. **`map_message` 的路线判断写的不够好**：之前的 `DLEFT` / `DRIGHT` 因为部分（P6）路口把判断标准搞宽松了，导致比赛现场把斜线的亮 4 个灯检测成右直线，提前转弯。
   - **建议**：改回，改回后正常不停车转弯 90 度可以完美过弯。

3. **调试性不足**：比赛现场人多，没办法跑完整流程（而我恰好输在了这里）。虽然我有 `mapdebug` 的开关可以跑部分路线，但是部分路线和完整流程的解耦仍然不明显，想要单独跑某段路线而忽略其他流程较难。比如过比赛现场通行牌这个地方和学校是差最多的，需要重点调试，而直接跑这里又会因为没扫二维码、扫完颜色走一段距离就直接停下，没法测试后半段的转弯情况。
   - **建议修改**：
     1. 重点实现门的单独调试
     2. 用一个额外的按钮，按一下跑一个节点，可以变相地跑完全程

### 二、本身方案的原因

1. **方案差距**：到了比赛现场你就会发现，全部都是用的灰度板 + 可升降结构来循迹的，优势比我们大很多。他们全程循迹 + 转弯陀螺仪可能都差不多了，而我们需要激光循迹板（障碍物上经常受干扰）+ 陀螺仪 + 灰度三重配合来走，对编程的要求更高，更难调。

2. **陀螺仪漂移**：陀螺仪有漂移，依赖多次撞板修正。虽然我们陀螺仪漂移也挺小了，但是确实比较依赖撞正；没转正的漂移程度大不大其实我也没量化过，但是换了他们那种方案的话可能比较难去依赖撞正。可以考虑高价钱搞个厉害一点的陀螺仪，或者在循迹的过程中多次采样来修正。

3. **车重与重心**：车的重量整体还是偏大，且重心偏高。之前低底盘调的好好的，加上上面的重量后很多速度需要重新调。建议换小点的电池，或者把铝板换掉，想办法把重心压低（同时提醒：轮距和那个高度的比值较为极限，走线建议留多点空间）。

### 三、学校场地问题

我们学校的场地用了很久也确实比较"狗屎"了，打了那么久没成绩老刘也不想投钱翻新。主要的差别：

1. 我们门那段距离偏短，角度有差
2. 除 7、8 平台宽度都偏小，且很多平台上有贴黄纸，345 好像是连起来的
3. 楼梯我们的比比赛的高一点，实际的更好走；珠峰第二层有护栏，走歪非常致命；珠峰底下有小门槛，而我们的没有（这个还是当时我现场加的，浪费了很多时间）

## 优化的方向

除了上面说的那些问题外，还有很多是我观察别人的车学来的（不全是）。

### 一、长直线特殊处理

P3 到 P4 大家很多都是直线冲刺且很直，而我们的在降速和碰到路口的时候还是有概率摇摆。

**解决**：
1. 碰到路口的摇摆就改循迹误差的判断标准，只看最中、左、右两个灯（一条线）（虽然照理我已经改了，但是实际还有问题）
2. 因为你提前知道要走的是大直线，所以可以特殊处理，比如在那段赋值特殊的循迹权重或者参数，以及考虑加陀螺仪获取摇摆幅度来抑制摇摆

### 二、转弯丝滑处理

今年冠军的弯道走的很丝滑，就跟开小车走线一个感觉。虽然我们的一次定位也不差，但是感觉那样子确实可以减少车身摇摆以及不丢速。

主要和我们差别应该是 **kp 的差别**（我们的 kp 偏大，转得猛一点）。他们估计是根据弯道角度大小赋予不同的 kp 然后转弯（kd 也肯定要加），再根据线的位置判断有没有转到位后切回循迹，走的很丝滑。

### 三、路线使用算法实时规划而不是事先写死

今年发现决赛的地图还是有较大变动，而我们一改地图，代码里面非常多路线也要跟着一起改（就算 ai 改也很耗时）。建议使用**最短路径算法**（障碍物可以加路程权重）来规划路线，彻底实现地图与代码的解耦。

**当前代码里已经这么做了**（见 [project_reference.md](project_reference.md) §9）：`nav_planner` 是 **point 式 Dijkstra**（转弯权重并入连接权 + 必经点 + 长度/障碍权重）；
`map_message` 的 `NavEdgeTbl[]` 是**唯一人工编辑源**，`nav_init()` 启动时自动构建执行层 `Node/ConnectionNum/Address`；`USE_PLANNER_ROUTE` **当前 = 1**。
⇒ 换地图只改边表 + `NAV_EDGE_COUNT` +（新增节点时）`map.h` 枚举，路线自动重算；PC 校验用 `validate/_weight_calib.py`、`validate/_check_csr.py`。
- ⚠️ **还没做完（2026-09-26）**：`plan_treasure_return()` 的 4 分支门梯、`get_newroute()` 回程的 8 分支门梯**仍是手写穷举**
  （思路：复用 `nav_set_edge_blocked()` + 一张门区边表换掉，路线应逐字不变）；`#if !USE_PLANNER_ROUTE` 的兜底块（约 127 行，不参与编译）去留未定。
- ⚠️ **规划层与执行层是两套东西**：开关只影响"路线怎么算"，`Navigation()` / `map_function()` / `getNextConnectNode()` 这层执行逻辑不受它影响。

### 四、升天的优化

搞个牛逼哄哄的视觉走一圈直接识别全部路牌（然后你就可以降维打击了）。不过用视觉来识别在平台或障碍物上的位置进行修正也确实可行，看实际情况来。

### 五、换个更好一点的电机和电机驱动

我们这个电机当时跑多了也是有问题，临近比赛的时候也花了我们不少时间。

### 六、代码进一步解耦

文件进一步分类，提高可读性、维护性、调试性、可迁移性（一个的方便传承，另一个是锻炼个人能力）。

## 0. 项目概述

### 0.1 赛题介绍

开始运行到二维码所在平台，获得另外两个存在线索的平台，然后经过指示牌自动规划路线，分别到两个平台，采集完线索合成最终宝物所在平台然后去拿宝藏，最后回家。第二轮根据第一轮获得的线索优化路线。

### 0.2 机器人简介

| 维度 | 说明 |
|------|------|
| **底盘** | 四轮直流编码电机。主要通过循迹板 + 陀螺仪闭环控制走直线或转弯，通过不同状态切换实现丝滑运动 |
| **导航** | 通过引导图导航，更改 `Navigation/map_message.c` 的 `NavEdgeTbl[]`（单数据源）即可更改小车路线（可选由最短路径算法生成，`Mission/config.h` 的 `USE_PLANNER_ROUTE`，路线决策在 `Mission/mission_planner.c`），具有较高的地图适应性 |
| **视觉** | 扫描二维码、数字和颜色（maxicam pro ） |

### 0.3 程序上电运行顺序

#### 为什么要有引导任务 + 临界区？

`main()` 调用 `vTaskStartScheduler()` 后就**不再返回**（FreeRTOS 接管），没法在 `main()` 里依次初始化 ⇒ 需要一个**引导任务**来完成后台初始化、派生其他任务：
**StartDefaultTask**（CMSIS 默认，CubeMX 生成、不要改，创建 `Start_task` 后自删）→ **Start_task**（用户引导任务，初始化完、任务创建完后自删释放栈）。套两层是为了**隔离 CubeMX 自动生成的代码**。

```c
taskENTER_CRITICAL();                    // ← 关调度器中断：保证三个任务一起创建完、一起就绪
main_task_create(); motor_task_create(); create_ArriveDetect_task();
vTaskDelete(NULL);                       // 自删
taskEXIT_CRITICAL();                     // ← 重新开调度器
```

若不关中断，刚建好 `main_task` 而 `motor_task` 还没建时调度器就可能切过去，此时 motor_task 不存在、全局资源也没初始化完。

---

```
上电/复位
  ├─ SystemClock_Config / HAL_Init / MX_GPIO_Init / MX_FREERTOS_Init    ← 均为 CubeMX 生成
  └─ vTaskStartScheduler()  →  StartDefaultTask（CMSIS 默认入口）
        └─ 创建 Start_task(优先级 6)，StartDefaultTask 自删
              └─ Start_task：
                   user_init()  → Encoder_init / Maxicam_Enable / imu_receive_init / motor_init
                                   + vTaskDelay(2000) 等稳定（含 IMU 上电自检：1s 无数据自动 IMU_Reinit 重试）
                   taskENTER_CRITICAL() → Rec_usart_init() → 创建三个任务 → vTaskDelete(NULL)
              → 此后并行：motor_task(优先级 6 / 5ms 实时闭环)、main_task(优先级 5 / 3ms 跑 Navigation())、
                 ArriveDetect_task(优先级 5 / 阻塞等 TaskNotify) —— 职责见 §4.2
```

## 2. 调试建议

### 2.1 调试顺序

先调底盘。`Chassis_api` 层已包装好，上层导航（main_task）通过调用 API(实际就是包装好的全局变量) 控制底盘(motor_task)，无需在意底层控制逻辑。
把底盘的每个速度的循迹都跑一跑，转弯的角度测一测，误差要缩小到可接受范围内。
先调内环再调外环，内环反应要迅速，不超调

### 2.2 工具建议

- **串口**：运行中调 PID 等参数非常有用，学会用环形缓存区。**预编译选项**：`main_task.c` 里有，可直接改值决定跑全程还是单功能调试。
- **改地图/看路线用图形化上位机**（`地图修改上位机/map_editor/`，用法见其 `README.md`）：拖节点改边表、按线索算完整路线、校验连通性、导出 C 代码、写回固件。
  ⚠️ 它写回 `config.h` 与布局文件有坑（**布局会盖掉固件地图**、写回曾吃掉 `config.h` 行尾注释把工程编挂）⇒ **用之前先看 [README.md](README.md) §3**。
- **上车前的校验脚本**：`地图修改上位机/validate/`（参考路线复现、CSR 连通性、必经点等价性、门回程 golden、`MAP_DEBUG` 路线正确性）。**改过边表/权重/路线后必须全部跑过再上车。**

### 2.3 电机调试

电机疯转时用调试器或串口看编码器值与输出占空比 —— 经验上**经常是编码器坏了**导致 PID 算出错。

- 调试时给电机 PWM **限幅**；占空比**不可以太大**，留 **15% 余量**（理由：① 烧线 ② 坏编码器 ③ 烧驱动板）
- 小车被障碍卡住要及时拿起来，否则堵转也可能烧线；**来回疯转**多半是 5ms 周期被破坏 ⇒ 查 printf 没删干净 / 单精度浮点 / 优先级是否最高
### 2.4 传感器调试

- **循迹板和圆形激光**: 可以通过拧螺丝调节焦距
- **陀螺仪**: 直接用串口 DMA 空闲中断读，
- **灰度传感器**: 灰度循迹并没有用到，只用于上下坡的陀螺仪角度微调

### 3.3 巡线传感器

- **16路 GPIO 读取**（0 = 黑线，1 = 白底）
- 权重表 `line_weight[16] = {-3...3}`，以车中心对称
- 有效值枚举：`VALID` / `ALL_ERR` / `POS_ERR`
- 详见 `scaner.c`

### 3.4 PWM 参数

- **频率**: 20kHz（TIM 配置: ARR=10800-1, prescaler=0）
- **正常运行**: `MOTOR_PWM_MAX = 8500`（PID 输出上限，`Chassis_Init()` 设置；旧文档的 9800 已过时）
- **转弯限幅**: 5000
- **堵转硬上限**: ≥8000 → 立即刹车死停（`STALL_PWM_ABSOLUTE_MAX`；⚠️ 堵转保护**当前是停用的**——代码在，调用点被注释掉，要用需取消注释）

## 4. 软件架构

### 4.1 四层解耦设计（由于历史原因当前解耦还不够规范，有能力的可以学学autosar架构并简单模仿）

```
任务层 + 导航层   Mission/ + Navigation/
    路线决策(mission_planner.c)、路径执行(Navigation())、门/障碍(barrier.c)、功能分发(map_function())、多轮竞赛
        │
        ▼
中间层            Application/chassis_api.c —— 统一运动控制抽象层（map.c 不知道底层 PID 细节）
    SetMode / SetTargetSpeed / SetTrackMode / MotorControl / Brake / DriveDistance
    EnableAntiSnake / EnableWheelieProtection
        │
        ▼
电机任务层        Task/motor_task.c —— 5ms 周期循环，实时控制
    读编码器 → 模式切换 → 巡线/转弯/陀螺仪 → PID → PWM；游龙算法 / 丢线保护 / 横滚保护 / 翘头保护
        │
        ├─ scaner.c（16 路巡线 / 巡线检测）
        ├─ turn.c  （原地 / 陀螺仪 / 循迹转弯）
        └─ pid.c   （增量式内环速度环 + 位置式外环巡线环）
```

> **分层说明**：最上层分两块 —— **任务层 `Mission/`**（`mission_planner.c` 路线决策 + `barrier.c` 障碍/门/`door()`）与**导航层 `Navigation/`**（`map.c` 的 `Navigation()`/`map_function()` + `nav_planner.c` 最短路 + `map_message.c` 单源边表）。下方 `chassis_api.c`/`motor_task.c`（底盘实时控制）与 `scaner.c`/`turn.c`/`pid.c`（传感器/转弯/PID）属控制层。口诀：Mission 决定"去哪"，Navigation 决定"怎么去"，Application 决定"怎么动"。

### 4.2 任务与调度

| 任务 | 函数 | 优先级 | 周期 | 职责 |
|------|------|--------|------|------|
| Start_task | `Start_task()` | 6 | 一次性 | 初始化 + 创建三任务后自删 |
| motor_task | `motor_task()` | 6 | 5ms | 编码器 → PID → PWM（核心实时任务） |
| main_task | `main_task()` | 5 | 3ms | `Navigation()` 路径执行（routetime=0/2 时） |
| ArriveDetect_task | `arrive_detect_task()` | 5 | 阻塞等待 | TaskNotify 唤醒后做到达检测 |

> **优先级说明**：FreeRTOS 数值越大优先级越高，`configMAX_PRIORITIES=7`（合法 0~6）。motor_task 与 Start_task 同为最高 6，main_task=5，主任务无法抢占饿死电机任务；ArriveDetect 也是 5。

### 4.3 核心数据流

```
map.c:Navigation() → Chassis_MotorControl(mode, Lspeed, Rspeed, aim)
                → motor_task: handle_xxx_mode()
                    → scaner.c:Go_Line() / turn.c:Go_Angle() / Stage_turn_Angle()
                        → 设置 motor_all.Lspeed / Rspeed
                    → handle_target_speed() → 写 motor_L0.target 等
                    → incremental_PID() → motor_set_pwm()
```

### 4.4 模式枚举与状态转移

```c
typedef enum { is_No=0, is_Free, is_Line, is_Turn, is_Gyro };
```

**巡线子模式**:

```c
TRACK_ALL=0         // 正常双边循迹
TRACK_LEFT_EDGE     // 左单边循迹（忽略右侧）
TRACK_RIGHT_EDGE    // 右单边循迹（忽略左侧）
TRACK_NEAR_CENTER   // 中心就近跟踪
```

`Nav_SegmentInit()` 的默认分支是 `TRACK_NEAR_CENTER`，绝大多数普通路段用“中心就近”跑；左右单边用于过门/贴边路段。`L_follow`/`R_follow` 循迹转弯代码保留但当前未启用。

**模式切换时的关键操作**:

| 来源→目标 | 处理 |
|-----------|------|
| Gyro→Line | gyroG_pid → line_pid_obj, TG→TC |
| Line→Gyro | line_pid_obj → gyroG_pid, TC→TG |
| Turn→Line | 清 line_pid / TC（**不清 `Cspeed`**，它由调用方设） |
| Turn→Gyro | 清 gyroG_pid / TG（**不清 `Gspeed`**） |
| →Turn | 清 gyroT_pid |

### 5.2 节点数据结构

相邻连接定义在 `Navigation/map_message.c` 的 `NavEdgeTbl[]`（**自描述：每行含 `from`**），一行一个连接：`{from, 目标节点, 标志位, 角度, 步长(cm), 速度, 功能}`。
各字段均用原宏/名（如 `LEFT_LINE|CRIGHT`、`SPEED1`、`UpStage`）；执行层 `Node[]/ConnectionNum/Address` 由 `nav_planner.c` 的 `nav_init()` 启动时自动构建（单数据源，不再手工同步三数组）。

| 字段 | 说明 |
|------|------|
| 目标节点 / 角度 | 从本节点出发到达的相邻节点 / 进入目标节点时的期望方位角（°） |
| 标志位 | 巡线模式、转弯方式、到达检测方式（见 5.3） |
| 步长 / 速度 | 本段路径长度（cm，用于里程判断）/ `SPEED0~SPEED5`（25~75） |
| 功能 | 该节点上要执行的障碍函数（`NONE`=普通路口） |

**例** — N5 的四行出边：
```c
/* N5->N4 */  {N5, N4, RIGHT_LINE|Temp_L|MUL2SING, 0, 84, SPEED3, NONE},
/* N5->N8 */  {N5, N8, CLEFT|DLEFT|DRIGHT, ANGLE_N5N8, DOOR_LEN_N5N8/2, SPEED1, DOOR},
/* N5->N12 */ {N5, N12, DLEFT|LEFT_LINE, 90, DOOR_LEN_N5N12/2, SPEED1, DOOR},
/* N5->N6 */  {N5, N6, MUL2SING|CLEFT|CRIGHT, 180, 150, SPEED2, NONE},
```

### 5.3 标志位解读

标志位是组合值，控制小车走到这一段时的行为：

| 标志 | 作用域 | 含义 |
|------|--------|------|
| `LEFT_LINE` / `RIGHT_LINE` | 全程 | 单边巡线模式（忽略另一侧白线干扰） |
| `NEAR_CENTER` | 全程 | 中心就近跟踪 |
| `Temp_L` / `Temp_R` | 过半切换 | 走一半后切换到单边巡线 |
| `TEMP_NEAR_CENTER` | 过半切换 | 走一半后切换为中心就近 |
| `L_follow` / `R_follow` | 转弯 | 循迹转弯（沿弧线拐弯） |
| `STOPTURN` | 转弯 | 停车后再原地转 |
| `NOTURN` | 转弯 | 到达后不需要转弯 |
| `MUL2SING` | 到达检测 | 线数从多条变成一条时判到达 |
| `MUL2MUL` | 到达检测 | 多条变多条（十字路口）|
| `DLEFT` / `DRIGHT` | 到达检测 | 左边/右边有线触发 |
| `CLEFT` / `CRIGHT` | 到达检测 | 左斜/右斜线触发 |
| `AWHITE` | 到达检测 | 全白区域触发 |
| `RESTMPUZ` | 动作 | 到达后重置陀螺仪 Z 轴 |
| `SLOWDOWN` | 动作 | 需要减速 |

#### ⚠️ `func` 必须有对应的 `map_function()` case（否则到点**静默什么都不做**）

`Navigation/map.c:map_function()` 的 `case` 只有：`NONE / UpStage / Bridge / Hill / SM / BSoutPole / QQB / BLBS / BLBL / DOOR / BHM / UpStageHome / View`，
其余全部落到 `default:`（空语句）⇒ 下面这些枚举值**写了也不会触发任何动作**：

| 没有 case 的 func | 边表是否在用 | 说明 |
|---|---|---|
| `LBHill` / `IGNORE` | 有 | 有意为之：`LBHill` 不触发爬坡（车不爬坡），只用权重区分楼梯；`IGNORE` 就是"忽略" |
| `BACK`（`S3/S4/S5→N14/N15/N16` 返回边） | 有 | 返回靠**负速度**（`-SPEED0`）倒着走，不需要动作 |
| `View1`（`N14→S3`、`N15→S4`、`N16→S5`、`N3→S1`、`N6→S2`） | ⚠️ 有 5 条 | 走这五条支路**不会触发直立景点动作**；`S1`/`S2` 由 `UPRIGHT_TOUR_ENABLE` 决定是否经过（默认不经过）⇒ 要用先补 `case View1` |
| `Special_node` / `DOOR1` | 无 | 预留 |

⚠️ **`View` 只标在 4 条直立景点边**（`C3→N14`/`N12→N16`/`N18→N16`/`B10→N14`）；景点支路 `N3→S1`(216cm)、`N6→S2`(120cm) 标的是 **`View1`**（动作通道）——
`do_Upright()` 只对 `nowNode == N14/N16` 分支，其余节点照走"**前进 19cm → 置到达**"，走 `S1`/`S2` **不能**复用它。
`S1`/`S2` 只在 `UPRIGHT_TOUR_ENABLE=1` 时才进 `wp`（默认关），**用 S1/S2 前先确认动作由谁做**（见 [README.md](README.md) §2.19）。

⚠️ **直立景点只在「宝藏已经取到手」之后才做**（`UPRIGHT_NEED_TREASURE`，`Mission/config.h`，当前 `1`）：
**一轮里一次都不做** —— 去程 `N12→N16`、回程 `N18→N16` 都还在取宝之前，只当普通节点直穿；
动作从「取宝那一刻」之后才开始做，所以实际是**第二轮各景点边各做一次**（串口会打 `[UPRIGHT] skipped: treasure not collected yet`）。
开关置 `0` 恢复旧行为（边表 `func=View` 就做）。判据是标志 `treasure_taken`，**不是 `treasure`**（`treasure` 是线索算出的宝物平台编号，`P7`/`P8` 读线索时就有值了）。详见 [README.md](README.md) §2.14。

⚠️ **「要不要绕 S1/S2」是另一个独立开关** `UPRIGHT_TOUR_ENABLE`（`Mission/config.h`，**当前 `0` = 不绕**）：
置 `1` 时一轮取宝**之后**按宝物平台绕近的那个（`P3`→`S1`、`P4`→`S2`；取宝之前一次都不去，规则上走错直接结束比赛），
二轮 `P3`/`P4` 之后固定两个都绕（里程 +806cm）。它只改**走位**：`S1`/`S2` 的 `func` 是 `View1`、`map_function()` 里没有 `case View1`
⇒ 车开过去**不做动作、不播报**，得分动作尚缺（要另写 `do_Upright1()`）。详见 [README.md](README.md) §2.19。

⚠️ **`Navigation/map.h` 的 `enum barriers` 只能往末尾追加成员**：`nav_planner.c` 的 `NavObsPenalty[]` 按**枚举值**直接索引（1..19），
中间插成员会让其后编号平移、障碍惩罚表整体错位（门又变"免费捷径"），而且**编译不报错**。当前顺序：
`NONE, UpStage, Bridge, Hill, LBHill, SM, View, View1, BACK, BSoutPole, QQB, BLBS, BLBL, DOOR, BHM, IGNORE, Special_node, DOOR1, UpStageHome`。

### 5.4 如何添加新路线(一般不需要)

**如果两个节点之间的连接已经定义在 `Navigation/map_message.c` 的 `NavEdgeTbl[]` 中**：

1. 在 `Navigation/map.c` 中声明一个新的 `u8 myNewRoute[100]` 数组
2. 按节点顺序填入节点名，以 `0xFF` 结尾
3. 在 `Mission/barrier.c` 的 `door()` 或对应逻辑中，根据门颜色结果调用 `Mission/mission_planner.c` 的 `load_route_at()` 加载这条路

**如果用导航规划器（`USE_PLANNER_ROUTE=1`）**：只需给出“必经点序列” `nav_plan_waypoints(route, 100, wps, n)`（wps 用节点名数组），逐段最短路自动拼出路线；`Mission/barrier.c` 的 `door()` 与 `Mission/mission_planner.c` 的 `get_newroute()` 现在就是这么写的。

**如果需要新增节点**：

1. 在 `Navigation/map.h` 的 `MapNode` 枚举中追加名称
2. 在 `Navigation/map_message.c` 的 `NavEdgeTbl[]` 中新增一行或多行连接（含 `from`）
3. 更新 `Navigation/map_message.h` 的 `#define NAV_EDGE_COUNT`
4. `ConnectionNum[]` / `Address[]` / `Node[]` 由 `nav_init()` **自动生成**，无需手工同步（索引与枚举严格对应由生成逻辑保证）

### 5.5 路线配置（当前活跃路线）

```c
// 当前初始路线
```

3. **第二轮开始**：`get_newroute()` 重建“巡游所有平台后回家”的路线（见 5.6）

### 5.6 多轮竞赛逻辑

`map.routetime` 记录当前跑图阶段：`0`=第一轮、`2`=第二轮全程、`3`=全部跑完停车。`mapInit()` 统一做地图状态初始化。

第一轮：初始 `route = {B1,N1,P1,N1,B2,N4,N5,0XFF}`，P1 二维码 → P3/P4 → 门区。`door()` 读 D2~D5/D1 后按门状态接线，前往 P5/P6/P7/P8 采线索，最后按线索回家。

第二轮：`main_task` 检测到 `map.routetime==1` 后调用 `get_newroute()`（其内部 `mapInit()` 会把 routetime 清回 0，所以必须**在调用后**再置 `map.routetime=2`）。`get_newroute()` 先调用 `door_set_pass_node()` 把 8 条门区通行边（N5↔N12、N5↔N8、N3↔N8、N3↔N10）置为 `function=NONE`（二轮过门不重触发 `door()`），再按门状态拼接：

```c
公共段 pre   = {B1,N1,P1,N1,B2,N4,N3,P3,N3,N4,N5,N6,P4,N6,N5}
东区巡游 tour = {N13,P5,N13,N12,N16,N18,B5,N19,C6,B7,N22,C9,P7,C9,N22,B6,N20,P8,
                  N20,C4,B11,C8,C7,B10,N14,C3,N9,B9,N7,P6,N7,B8,N9,N10}
```

- 非 P6 宝藏：进下半区 `entry` 用 `N12`（D2 进）或 `N8→N12`（D3/最外进），最后 `N10` 回程
- 宝藏=P6：进下半区经 `N10` 直达（`entry_D2_p6={N12,N11,N10}`、`entry_D3_p6={N8,N10}`、`entry_far_p6={N4,N3,N8,N10}`），巡游用 `tour_p6`（先深入 P6 再 P8→P7→P5 绕回，终点 N12），回程避开 N11 刀山
- 9 个门状态分支各自拼接 `pre + entry + tour + tail`，`build_round2_route()` 写入 `route[]`

二轮全程 `routetime==2` 使 P7/P8 的 treasure 改路（`map.routetime==0` 门槛）不触发，路线不被截断；跑完 `Nav_TurnAndAdvance()` 使 `routetime→3` 即停，不会无限重启二轮。

`scaner.c` 中 16 路 GPIO 的**权重表 `line_weight_default[16]`** 决定了巡线修正力度，这个权重可以先按物理长度来，然后看跑的情况加大或减少部分，一直偏向一边就中心加大，大摇摆就可以边缘减小，贴线抖动可以中间减少，其实现在的权重也没有特别严谨，就是看感觉

## 9. 算法与理论基础

### 9.1 PID 基本概念与项目里的用法

**内环：增量式速度 PID（`pid.c: incremental_PID`）** —— 5ms 周期采样编码器速度 `measure`、目标 `target`，误差 `bias = target - measure`；算的是输出的**增量**：

```text
Δu = Kp × (e_k - e_{k-1}) + Ki × e_k + Kd × (e_k - 2×e_{k-1} + e_{k-2})
u_k = u_{k-1} + Δu
```

- 输出累加、天然带积分效果，且不会像位置式那样出现大的输出阶跃 ⇒ 控制电机一般用增量
- 加了抗积分饱和：输出已到上限时，只允许积分朝"能退出饱和"的方向积分
- `target==0` 且测量很小时把输出/历史清零，防止停车后残留 PWM 抖动

**外环：位置式航向 PID（`pid.c: positional_PID`）** —— 巡线外环输入传感器误差、输出左右轮差速 `Fspeed`；陀螺仪外环输入角度误差。
位置式输出 `u = Kp×e + Ki×∫e + Kd×差分`；项目给微分项加了**一阶低通滤波**（`differential_filterK=0.5~0.7`），避免传感器噪声直接放大进差速。

### 9.2 为什么外环输出要按速度缩放

`Go_Line()` 里 `Fspeed *= |speed| / 40`、`Go_Angle()` 里 `GGspeed *= |speed| / 50`（40/50 其实没用，关键是"乘速度比"这一步）。
差速转向时 `ω ≈ (v_right − v_left) / 轮距` ⇒ 差速固定而车速提高会让转弯半径变大、路径形状变化；把差速按速度比例缩放后，**同样的航向误差在不同车速下产生近似相同的曲率**，路径形状基本与速度无关 —— 这就是调一个 PID 能覆盖多个速度档的理论基础。

### 9.3 巡线误差为什么用 5 个历史值

`scaner.c` 维护 `line_data[5]` 滑动窗口：每帧误差先过 `coarse_filter`（灯数/线数明显异常判无效）→ `pos_detect()` 做位置连续性检查（与最近一次有效位置差 > 1.5 格判跳变）
→ `Get_scaner_error()` 对 5 个值做"多数决 + 簇投票"（正确值多就取正确值平均；没有则用位置跳变值里**最密集的簇**作候选）。
全部无效时返回**上一次有效误差**而不是 0 —— 丢线瞬间保持最后航向，避免突然直行冲出。本质是"时间滤波 + 空间聚类"：单帧噪声很难同时骗过两者。

### 9.4 寻中线为什么“只取最中心 2 灯”--一般用于走直线，不希望干扰

规则见 **§6.4**（同一套 `calc_near_center()`），这里只讲为什么：整段平均会让粗线/旁线把中心点拖偏，强制误差 0 又不修正偏心细线；取"连续亮灯段内最靠中心的 2 灯"是两者的平衡 —— 线粗时仍追踪中线，来干扰时不被拖走。

### 9.5 速度阶梯 PID 的理论动机

同一套参数满足不了高速和低速（高速要低 Kp/Kd 防摆、低速要高 Kp 跟线）。用**实际速度**而非目标速度取档的原因见 §6.2：减速有惯性，刚发减速指令就切低速高 Kp、车还很快时会振荡，只有实际速度真降下来再切才稳。

### 9.6 游龙防抖（AntiSnake）

`|Scaner.error| > 1.0` 时累计 `anti_snake_err_count`（回正后快速衰减）；达阈值后把 `motor_all.Cspeed` 降到目标速度的 1/3（最低 15），
必要时 `OverrideLinePid(30,0,180,30)` 强压 PID；恢复后回到 `target_speed` 并恢复 PID。本质是"检测到持续横向误差 → 主动降速提高阻尼 → 恢复"。

### 9.7 转弯算法的细节

- `need2turn(now, target)` 把角度差归一到 `(-180, 180]`，保证走最短旋转路径
- `Turn_Angle_Base()`：误差 < 2° 判到位；输出太小但误差仍存在时给固定 ±7 死区补偿，避免低速摩擦导致停在中间
- `Stage_turn_Angle()` 传 `force_threshold=150`：偏离超过 150° 时强制向右转（只是为了每次转的方向一样）
- `Turn360Step()` 用梯形速度曲线：加速 40° → 全速 → 358° 前减速，比固定 PID 脉冲更平稳、末端不冲

### 9.8 里程与长度标定

`Distance += (encoder_avg × 10.4 × π / 5720) / 0.362 × LEN_SCALE`
编码器每圈 5720 脉冲、减速比 0.362、轮径 104mm；`LEN_SCALE=1.2` 是实测标定（100 代码单位 ≈ 120cm）。地图 step 与所有距离阈值已按厘米内联折算，只有运行时连续累加的里程公式乘 `LEN_SCALE`。

### 9.9 IMU 与角度补偿

`basic_y/basic_p/basic_r` 是上电零位校准（10 次采样平均），`imu.compensateZ` 由 `mpuZreset()` 算出，使 `getAngleZ() = yaw + compensateZ` 归一到 `[-180,180]` 并等于参考角。转弯、陀螺仪直行、角度判断都基于 `getAngleZ()`，所以上电后必须等 IMU 数据稳定再做 `IMU_Calibrate_Yaw()`。

### 9.10 FreeRTOS 实时性与性能

- motor_task 优先级 6、用 `vTaskDelayUntil` 固定 5ms 周期，main_task 优先级 5 不会抢占饿死它；**5ms 循环里别做阻塞操作或大量 `printf`**（拖慢周期）
- Cortex-M7 的 DWT 周期计数器默认锁写，测 CPU 耗时要先 `DWT->LAR = 0xC5ACCE55`
- M7 只有单精度 FPU：浮点常量写 `f` 后缀、用 `fabsf/sinf/strtof`，避免软件 double 拖慢中断与 PID

## 10. 竞赛实操笔记

### 10.1 常见调参流程


## 11. 常见问题 FAQ

**Q: 小车不走直线？** 见 §10.1「车跑偏」的检查链：权重表 `line_weight_default` → 当前档 kp/kd（按实际速度取档）→ 四个轮子 PWM 一致 → 机械结构。

**Q: 电机疯转怎么办？** 串口观察编码器值是否异常（大概率是编码器坏导致 PID 算出错），先限幅再排查。

**Q: 不同场地需要改什么？** 主要是 map 里的距离补偿。⚠️ **先读 [project_reference.md](project_reference.md) §14**：约一半的"距离"可由 `Δ = 19(1−cosφ) + d(判据)` 直接算（平地 + 段长≥20cm + 转弯 100°~178°），不用一场地一手调；
剩下算不出来的（段长太短、障碍/平台上、门区）才保留实测。该机制由 `TURN_CALC_ENABLE` 控制，**当前 = 0（没在跑）**。

**Q: 二轮过门被误判/直冲某节点？** 先看 `door()` 的状态判定（按 lastNode/nowNode 精确匹配）与 `get_newroute()` 预设的 `door_pass[]`，再查门区段 `DOOR_LEN_*`/`ANGLE_*` 宏；改完路线务必按连接表逐边核对。
