## 0. 结论

当前地图和路线全部硬编码在代码里，不是从配置文件读取的。决赛如果只做“微调地图”，通常只需要改：

1. `../Application/map_message.c`：路段连接、长度、角度、速度、节点功能。
2. `../Application/map_message.h`：门区段长度/角度宏。
3. `../Application/map.c`：初始路线、门分支路线、转弯前补偿距离。
4. `../Application/barrier.c`：第一轮 QR/门/宝物改路，第二轮拼路。

你把新地图或差异信息给我后，我可以按第 5 节的流程直接修改，并在最后给你一份“改了什么、哪些值需要现场确认”的清单。

## 2. 地图数据模型

### 2.1 节点编号

代码里共 52 个节点，枚举顺序就是索引值，**不能随便调换**：

```c
S1=0,  P1=1,  N1=2,  B1=3,  B2=4,  B3=5,  N2=6,  P2=7,  S2=8,  P3=9,
N3=10, N4=11, N5=12, N6=13, P4=14, N7=15, P6=16, B8=17, B9=18, N8=19,
C1=20, C2=21, C3=22, N9=23, N10=24, N12=25, N13=26, P5=27, N14=28, S3=29,
S4=30, N15=31, S5=32, C4=33, C5=34, B4=35, B5=36, B6=37, B7=38, N16=39,
N18=40, N19=41, P7=42, N20=43, N22=44, C6=45, C7=46, C8=47, C9=48, P8=49,
N11=50, G1=51
```

### 2.2 连接表 `Node[126]`

每一行是一条**有向边**，格式为：

```c
{目标节点, flag, angle, step, speed, function}
```

示例：

```c
/*N5 13*/ {N8, CLEFT|DLEFT|DRIGHT, ANGLE_N5N8, DOOR_LEN_N5N8/2, SPEED1, DOOR},
```

含义：从 N5 出发到 N8，使用该 flag 巡线，到达 N8 时期望方位角由 `ANGLE_N5N8` 决定，这段长度 `DOOR_LEN_N5N8/2`，速度 `SPEED1`，到达 N8 后执行 `DOOR` 功能。

### 2.3 邻接索引

`ConnectionNum[node]` 是该节点的连接数，`Address[node]` 是该节点第一行在 `Node[]` 中的下标。**增删连接时必须同步更新这两个数组**，否则 `getNextConnectNode()` 会找不到边，甚至返回 0。

### 2.4 路线数组 `route[]`

```c
u8 route[100] = {B1, N1, P1, N1, B2, N4, N5, 0XFF};
```

- 每项是“下一个要到达的节点”。
- 相邻两项必须在 `Node[]` 里存在一条有向边。
- `0xFF` 是结束符，跑完后 `map.routetime` 加 1。
- `mapInit()` 在非调试模式先把车放在 `N2`（从 P2 出发），所以 `route[0]` 应是 N2 能直达的第一个目标，例如 `B1`。

## 4. 常见修改场景

| 场景 | 改哪里 |
|------|--------|
| 某段路变长/变短 | `map_message.c` 对应边的 `step`，单位已经是 cm |
| 某段转弯角度变了 | `map_message.c` 对应边的 `angle`；门区段改 `map_message.h` 的 `ANGLE_*` |
| 某段速度不合适 | `map_message.c` 对应边的 `speed`，用 `SPEED0~SPEED5` |
| 某段巡线方式不对 | 对应边的 `flag`，如 `LEFT_LINE`、`RIGHT_LINE`、`NEAR_CENTER`、`Temp_L/R` |
| 某个节点新增/删除 | `map.h` 枚举、`map_message.c` Node 表 + `ConnectionNum` + `Address` |
| 门位置/数量变了 | `map_message.h` 宏、`door()` 状态机、`door_pass[]` 下标含义、各门分支路线 |
| 第一轮路线变了 | `map.c` 初始 `route[]`、`barrier.c` 的 QR/门/宝物改路函数 |
| 第二轮路线变了 | `barrier.c` 的 `get_newroute()` 里 `pre/entry/tour/tail` |
| 平台编号换了 | 节点连接表 + 所有引用该平台编号的路线和 `treasure` 判断 |
| 只是换场地、节点没变 | 通常只需改 `step`、`angle`、门区宏和路线数组 |

## 5. 我收到新地图后的修改流程

1. 先读新图/新说明，和当前 `Node[]`、`route[]` 做差异对比。
2. 更新 `map_message.c` 连接表：只改有变化的边，保留没变的边。
3. 同步更新 `ConnectionNum[]` 和 `Address[]`，增删节点时更新 `map.h` 枚举。
4. 更新 `map_message.h` 门区宏。
5. 更新 `map.c` 的初始路线和门分支路线。
6. 更新 `barrier.c` 的动态改路函数和 `get_newroute()`。
7. 逐边核对连通性：每条 `A,B` 都能通过 `getNextConnectNode(A,B)` 找到。
8. 核对方向：`Node[]` 是有向边，反向走要单独存在或能通过角度宏派生。
9. 编译，预期 0 Error 0 Warning。
10. 输出“改动清单”，标出需要现场实测的 step/angle/速度。

## 6. 你告诉我地图变动时，最好包含这些

1. 新地图图片或文件路径，以及图中能看到的节点编号/平台编号。
2. 平台位置是否变化：P1~P8 各在哪个区域。
3. 门/通行指示牌：数量、位置、方向、颜色数量，是否还按 D1~D5 命名。
4. 路段长度：哪些路变长/变短，最好给 cm 或图上比例。
5. 转弯角度：哪些岔路角度变了。
6. 障碍物：桥、山、跷跷板、波浪板、南极、直立景点等的位置和类型。
7. 两轮策略是否要改：第一轮采集顺序、第二轮巡游顺序、回家路线。
8. 规则里临时新增的约束，例如“必须按某顺序经过平台”。

如果只有图片，我会尽量用图片文件名和现有节点表做推测，但关键数值仍需要你确认，尤其是长度和角度。

## 7. 改完必须核对

- 每条路线以 `0xFF` 结尾，长度不超过 100。
- 相邻节点在 `Node[]` 中存在有向连接。
- 新增节点时枚举、`ConnectionNum`、`Address` 三者顺序一致。
- 门区段长度/角度只改宏，不要改散落的手工值。
- 门区段有 8 条双向边：N5-N12、N5-N8、N3-N8、N3-N10。
- 反向路段角度与正向相差约 180 度，`ANGLE_REV()` 会自动算。
- 平台/南极结束后保留 `nodes.nowNode.function`，不要误清。
- 改完 `route[]` 后，`mapInit()` 的起始节点逻辑不能冲突。

## 8. 当前路线速查

### 8.1 第一轮初始

```c
{B1, N1, P1, N1, B2, N4, N5, 0XFF}
```

P1 读 QR 后：

| QR 百位 | 去向 |
|---------|------|
| 3 | 先去 P3，再到 N5 门区 |
| 4 | 先去 P4，再到 N5 门区 |
| 0 | 跳过 P3/P4，直接到 N5 门区 |

### 8.2 第一轮线索平台

QR 十位/个位决定先去 P5/P6，再去 P7/P8：

| 线索 | 路线数组 |
|------|----------|
| A=5, B=7 | `rout_57` |
| A=5, B=8 | `rout_58` |
| A=6, B=7 | `rout_67` |
| A=6, B=8 | `rout_68` |

`update_route_at_door_for_stageAB()` 会根据 D2/D3/D4 是否可过，在前面补 `N11,N10` 或 `N10` 等入口。

### 8.3 门分支

当前实际被调用的门路线数组：

```c
door1route = {N3, N8, 0XFF};
door6route = {N4, B3, N2, P2, 0XFF};
door7route = {N8, N3, N4, B3, N2, P2, 0XFF};
door8route = {N4, B3, N2, P2, 0XFF};
door11route = {N5, N4, B3, N2, P2, 0XFF};
```

`door2route`、`door3_1route`、`door4route`、`door5route`、`door9route`、`door10route`、`door12route` 目前只保留未调用，改图时可以保留，不作为现场主路线。

### 8.4 第二轮拼接

`get_newroute()` 按“公共段 + 进东区 + 东区巡游 + 回家尾段”拼接：

```c
pre   = {B1,N1,P1,N1,B2,N4,N3,P3,N3,N4,N5,N6,P4,N6,N5}
tour  = {N13,P5,N13,N12,N16,N18,B5,N19,C6,B7,N22,C9,P7,C9,N22,B6,N20,P8,
         N20,C4,C8,C7,N14,C3,N9,B9,N7,P6,N7,B8,N9,N10}
```

宝藏=P6 时改用 `tour_p6`，入口和尾段也按宝藏位置选择；9 个门状态分支在 `get_newroute()` 里各自拼接。

## 9. 调试开关（现场注意）

当前源码实际值：

```c
MAIN_DEBUG   = 1   // main_task.c，主任务跑调试分支，不会执行 Navigation()
MAP_DEBUG    = 0   // map.h
SKIP_ROUND1  = 0   // map.h
DEBUG        = 0   // barrier.c，门颜色走真实摄像头
```

⚠️ `README.md` 和 `project_reference.md` 写的是 `SKIP_ROUND1=1`，但当前 `map.h` 源码是 0，现场以源码为准。正式比赛前必须把 `MAIN_DEBUG` 改回 0，否则不会跑图。
